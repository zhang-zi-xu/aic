### 数据结构变化（v1 → v2）

- `farm_tasks` 新增：`status`、`time_window`、`materials`、`risk`、`evidence`(JSON)、`plan_item_id`、`updated_at`、`confirmed_at`、`executed_at`、`completed_at`。

- 新表 `task_records`；新唯一索引 `idx_tasks_plan_item(source_message_id, plan_item_id) WHERE 两者非空`（SQLite 视 NULL 为互不相同，历史任务不会互相冲突）。
- `schema.sql` 未改动：迁移服务自己完成建表/加列，因此新库与老库两条路径都走同一套幂等逻辑。

## 三、真机闭环验证（真实后端 + 真实数据库）

脚本逐步调用真实 HTTP 接口（临时探针任务，验证后即删除），结果如下：

```
田块：乙田（小麦） id=f-c353e7ec-4992-4173-b937-fd7724875db6
1) 登记方案项（AI 草稿→待确认）        -> HTTP 201 status=pending_confirmation
2) 同一方案项重复登记                  -> HTTP 200 复用同一条任务（幂等）
3) 无执行记录直接标「已执行待复查」      -> HTTP 409 「已执行待复查」必须由提交执行记录进入，不能直接改状态
4) 确认安排                            -> HTTP 200 status=pending 有确认时间
5) 提交执行记录                        -> HTTP 200 status=awaiting_review 有执行时间 记录田块=乙田
6) 提交复查记录（结论：明显好转）        -> HTTP 200 status=completed 有完成时间 记录数=2
7) 追溯                                -> sourceMessageId / planItemId / 田块 / 时间窗口 / 两条记录齐全
8) 已完成任务再补执行记录               -> HTTP 409 任务已完成，如需再执行一次请先把状态改回待执行
9) 删除探针任务                        -> HTTP 200 剩余 7 条（用户数据未受影响）
```

**结论：一条方案项 → 任务 → 执行记录 → 复查记录 → 完成，全程可追溯；状态推进只由用户提交的事实驱动，AI 无法宣告完成。**

界面侧另用无头浏览器按真实接口数据渲染任务页核对：进行中筛选下显示"当前没有进行中的任务"（用户任务均为迁移来的完成态），已完成筛选下逐条显示「已完成」徽标、执行条件/操作方法/复查要点、`依据：这条方案没有附来源ID`（不编造依据）、以及「重新打开 / 在对话里讨论」操作。

### 覆盖的关键负路径

- 提交执行记录前不能进入「已执行待复查」；没有执行记录不能提交复查记录；已完成任务不能重复提交执行记录；已取消任务不能提交任何记录。
- 任务名称必填、日期格式、关联田块必须存在；记录内容必填、类型只能是 execution/review、复查结论取值受限。
- 依据只能来自真实来源库：客户端伪造的 `chunkId` 被剔除（`forgedEvidenceIsDroppedAndRealChunkIsKept`）。
- 删除任务时执行/复查记录一并清理，不留孤儿。

## 五、顺带修掉的三个问题（都不是 P2 新引入，但会影响验收可信度）

1. **测试会写用户的真实数据库**：`CostGuardTest`、`RagPipelineTest` 是 `@SpringBootTest` 但没有覆盖数据源，运行时会连 `./data/nongxin.db`，其中成本护栏测试还会写入 `answer_cache`。已改为临时库（`@DynamicPropertySource`），并清理了当时写进真实库的那条缓存行。
2. **`ChatControllerTest` 全红**：`ChatController` 为了避开并行开发冲突改用字段注入 `ApiKeyService`，手工 `new` 出来的控制器里该字段为 null，18 条用例中 15 条失败。已在测试侧注入"用户自带 Key 直接放行"的实现，成本护栏本身仍由 `CostGuardTest` 覆盖。
3. **`done` 与 `status` 双事实源风险**：迁移时直接把 `done` 并入 `status` 并删列，避免两个字段各说各话（旧 jar 进程已停，不会再有旧代码写 `done`）。

## 七、真实模型联调记录（2026-09-11 补测，deepseek-chat）

三轮真实对话，全部经由运行中的后端与真实数据库（探针任务在结束时删除）：

| 轮次 | 用户输入 | 结果 |
| --- | --- | --- |
| 1 · 方案 | 「水稻刚破口，稻瘟病怎么防？位置和这周预报已补上，请给我这几天的防治方案，包含时间窗口、所需物料、复查要点，我要点加入任务，缺的写待确认」 | 提交 5 项处方单：`itemId` 由服务端注入 p1–p5，`window`/`materials` 齐全，缺的地方写「待确认（药剂品种、器械需按当地有效登记标签选定）」，依据为真实来源 ID |
| 2 · 报告已执行 | 「按你给的方案，我今天上午已经打完第一次药了，接下来怎么安排？」 | 回答转向复查与下一窗口（「今天下午这一趟别省：重点看穗颈有没有发黑、有没有白穗…这直接决定第二次药是 9/15 打还是提前」），**没有再让用户去打一次已经打过的药** |
| 3 · 复查变差 | 「今天复查发现病斑反而往上部叶片扩展了，是不是打得不对？要不要换药、什么时候补打？」 | 「补打这件事，**别等**——按全国农技推广服务中心的方案（chunk-pest-rice-blast），发病严重田块在首次施药后 7 天左右就该上第二次药，您现在已经是第 5 天复查、病还在扩，属于该动手的节点；同时浙江本地指导意见（chunk-zjagri-pest）也强调抽穗灌浆期要抢晴及时用药」 |

**7.1 方案项字段规范**：模型没有编造物料与用量，缺失一律落成「待确认」；依据 ID 经服务端白名单校验后原样进入任务（`依据保留=["chunk-pest-rice-blast","chunk-draft-rice-blast"]`）。

**7.2 任务与记录确实进入了对话上下文**：第一轮回答里模型主动指出「档案里 9/15、9/16、9/18 那三条「已完成」记录日期在今天之后，麻烦您核对下是不是填错了」——它读到的是用户真实任务与状态，而不是我告诉它的。

**7.3 复查结果改变了建议**：第三轮把"齐穗期补第二次"提前为"这几天挑风小时段补打"，并说明了触发变化的事实（第 5 天复查、病还在扩）与依据（两个来源 ID）。这正是 P2 要求的"说明哪里变了、为什么变"。

**7.4 用药红线仍守住**：三轮回答均未给出具体药剂剂量，统一收尾为"具体药剂与用量，以当地登记标签为准"。

**7.5 需要改进但不阻塞验收（已修复并复测）**：第三轮给出的动作是明确可执行的，模型却没有调用 `submit_farm_plan`（用户因此拿不到「加入任务」入口，只拿到一张确认卡）。原因是它想先知道第一次用的是什么药；这与提示词里"缺少的信息写待确认、也要提交处方单"存在张力。

**修复与复测（2026-09-11 09:33）**：
- 提示词补一条硬规则「追问不是推迟给方案的理由：**确认卡与处方单可以在同一轮一起提交**；给出了带时间/条件的动作就必须同时调用 `submit_farm_plan`，未定字段写「待确认」」，`submit_clarify` 的工具返回文本同步补上同一句；单测锁定这些句子，防止回退。
- 复测方式与真实界面一致：**带多轮历史**（把此前的确认卡与处方单按前端 `requestHistory` 的格式折进 assistant 消息），三轮 `deepseek-chat` 真实对话。
- 结果：第一轮处方单 4 项 + 确认卡；第二轮"第一次药已打"后再交 3 项后续安排；**第三轮（复查变差）提交了 4 项补治处方单**（`itemId` p1–p4、含 9/13 避开降雨的窗口与依据来源），标题即「第一次药后病斑上移」——用户能直接点「加入任务」。
- 结论：7.5 关闭。注意上一轮复测**没有带历史**，因此无法触发"同一会话连续追问不超过 2 轮"这条规则；带历史后模型行为符合预期。

**7.6 说明（避免误判为缺陷）**：本轮复测同样观察到模型每轮都会发确认卡，这是"信息确实缺失（药剂类型、抽穗进度、位置）"的正常追问，且已与处方单同轮给出，不再阻塞「加入任务」。

**7.7 密钥与数据安全**：测试 Key 只作为进程环境变量传入，从未写入任何文件；跑完后核对——后端日志（含轮转文件）出现该 Key **0** 次，数据库 `conversations / farm_tasks / task_records / answer_cache` 文本扫描 **0** 处。5 条探针任务及其记录已全部删除，任务数回到 7 条、记录 0 条。

**7.8 顺带发现，需要你决定的一件事**：迁移前你的 7 条任务 `done` 全部为 1，其中 3 条日期（9/15、9/16、9/18）在今天之后——迁移按原样转成了「已完成」。如果那不是你本人的标记，可以在「农事任务」里对这几条点「重新打开」，退回待执行；我没有替你改数据。
