## 一、范围决策：为什么不做 YOLO 自训练检测

竞赛评分表（`docs/规则提取.txt`）里「AI 技术应用」只占 20 分，考察的是**匹配度、方案严谨性与可复现水平**；「需求分析 + 项目实施 + 研究结论与应用成效」共 45 分，全部指向真实调研与落地闭环；「创新性」25 分明文认可**模式创新**。

- 用公开数据集（多为实验室摆拍单叶）训练的检测器，一上真实田间手机照片就会掉点，评委问一句"数据来源与你场景是否一致"就丢分；
- 生态位重复：YOLO + 农作物识别是这类比赛的常见选题；
- 与项目既有红线冲突：本项目一贯"不把未知当事实、不给假置信度"，而单图分类器输出"稻瘟病 92%"正是反面。

**结论**：走视觉大模型路线，把"图上能看到的 / 可能原因 / 还需什么"讲清楚，并与已有"建议—任务—执行—复查"闭环咬合。真实照片数据集的正确用途是**评测素材**（检验模型会不会看着一张图就乱下诊断），不是训练数据。

### 4.4 过程中的一次自我纠正

第一次联调我误选了一张标题含 "Rice blast" 的 Wikimedia 文件，实际是**实验室照片**（显微镜前的科研人员）。模型如实描述成"实验室场景、屏幕上荧光成像不是叶片病斑"，并提醒"这张可能发错了"——这既是图片链路确实生效的证据（后端日志 `images=1`），也说明"不凭图编造作物症状"这条规则在真实模型上生效。随后换成真正的病叶照片重新跑完整流程。

## 五、已知限制与后续

1. **视觉名单是经验名单**：`VisionSupport` 里的 DeepSeek 型号是 2026-09-11 用真实 Key 实测确认能接受图片输入的（1×1 像素图会被供应商判为无效图，正常照片返回 200）。新模型不可能自动覆盖，所以保留了用户在「模型设置」里的强制开关；被拒绝时文案给出明确出路。
2. **HEIC/WEBP 不支持**：ImageIO 不解码 WEBP，iPhone 的 HEIC 也无法直接读；当前策略是客户端统一转 JPEG，服务端明确拒绝并提示用户"相册里转存或截图后再传"。若真实用户反馈这一步太麻烦，再考虑引入解码库。
3. **附件没有账号隔离**：接口仅监听本机回环地址，P4 做多用户与鉴权时需要给上传接口加归属校验与配额。
4. **图片不进入历史轮次**：只有当前这一轮携带原图，历史结论以文字形式保留——省流量与费用，但也意味着"翻回去改问法"需要重新上传。
5. **未做**：图片里自动识别农药包装文字、EXIF 里的拍摄时间参与物候判断、附件导出——都属可选增强，未在 P3 范围内。
6. **真实用户验证缺口**：目前没有农户实测反馈，评分表里「应用成效」15 分仍缺佐证材料；建议尽快找一个真实使用者试用（手机访问 + 拍照提问 + 提交一次执行/复查记录），把反馈截图与记录作为佐证。
