# RAG 检索评估方法与口径

> 本文说明「农心 Agent」检索能力的评估方式、当前结论的适用范围，以及配置真实语义模型后的复测步骤。
> 目的是让每一个对外引用的数字都有可复现的来源与明确的口径边界。

## 一、为什么要先做评估

知识库最初的检索只有「关键词加权 + 元数据过滤」。要引入向量语义召回，必须先回答一个问题：
**它到底有没有用、在哪些场景有用？** 没有评估就上线向量检索，等于用一个不可解释的黑盒替换一个可解释的规则——
一旦召回质量下降，既无法定位原因，也无法对使用者交代。

因此本项目的做法是：**先把评估能力和口径定下来，再让向量进入检索链路**。

## 二、评估设计（三条原则）

### 1. 同深度对照

基线与混合检索使用**相同的召回条数**（默认 `depth=5`）。

初版评估让关键词路受「标题/关键词级命中」约束、混合路有三条通道投票，实际是「让基线被卡死、再看混合路胜出」——
这种比较没有意义。修正后两条路径都在同等条件下比较。

### 2. 用例分型（关键）

评估集里的每个用例标注类型：

| 类型 | 含义 | 命中意味着什么 |
| --- | --- | --- |
| `literal` | 提问中含字面线索（如「叶」「白」「虫」「积水」与资料用词重合） | 字符级相似即可召回；**能命中只说明检索管线有效** |
| `semantic` | 提问与资料术语**零字面重合**（如「禾苗蔫头耷脑，叶尖先黄后枯」） | 需要真正的语义理解；**只有真实 embedding 模型命中才算数** |

**本地哈希向量（离线兜底实现）在 `semantic` 类上的命中不计入有效成绩**——
它靠的是字符重合，不是语义能力。把它算作语义成绩会得出误导性结论。

### 3. 标注向量类型

报告中明确给出 `vectorKind`：

- `local-hash`：本地哈希实现（`NONGXIN_EMBEDDING_MODE=local`），离线可跑，**仅用于链路自检与断网演示**；
- `remote-model`：真实 embedding 模型（如 `BAAI/bge-m3`），结果可用于说明语义检索效果；
- `none`：未启用向量路，此时 hybrid 列与 keyword 列完全相同（纯关键词检索）。

## 三、当前状态与结论边界

| 项 | 状态 |
| --- | --- |
| 关键词检索 | 已实现（含作物硬过滤、地区亲和、已核验原文优先） |
| 混合检索（关键词 + 向量 + 图谱，RRF 融合） | 已实现，接口契约不变，向量不可用时自动降级 |
| 本地哈希向量模式 | 已验证可用（44 个片段索引成功，检索管线跑通） |
| 真实语义模型 | **尚未验证**：需要配置 `NONGXIN_EMBEDDING_KEY` 后复测 |

> ⚠️ 在配置真实语义模型之前，**任何"命中率提升"的数字都只能表述为「检索管线自检结果」**，
> 不得作为"语义检索效果"写入方案或答辩材料。

## 四、复测步骤（配置真实模型后）

1. 配置密钥并重启后端：

   ```bash
   set NONGXIN_EMBEDDING_KEY=sk-xxxx        # 硅基流动等 OpenAI 协议兼容平台
   set NONGXIN_EMBEDDING_MODEL=BAAI/bge-m3  # 默认值，可替换
   java -jar target/nongxin-agent.jar
   ```

2. 查看索引与图谱状态：

   ```bash
   curl http://localhost:8080/api/kb/status
   # 关注：vectorReady=true、indexedChunks、graph.entityNodes
   ```

3. 触发索引（若启动时未自动完成）：

   ```bash
   curl -X POST http://localhost:8080/api/kb/reindex -H "Content-Type: application/json" -d "{}"
   ```

4. 运行评估（可调召回深度）：

   ```bash
   curl -X POST "http://localhost:8080/api/kb/eval?depth=5"
   ```

5. 记录三个数字：`literal` 命中率（keyword → hybrid）、`semantic` 命中率（keyword → hybrid）、平均召回条数。
   `vectorKind` 应为 `remote-model`，否则结果不能用于对外表述。

## 五、仍存在的口径局限（如实记录）

1. **判定方式较粗**：当前以「Top-K 中是否含期望关键词」判定命中，未做人工相关性标注。
   更严谨的做法是标注「哪条资料真正相关」，据此计算准确率（precision）与召回率（recall）。
2. **未统计无关条目占比**：混合检索可能同时带回无关条目，报告中的「平均召回条数」只能部分反映这一点。
3. **评估集规模有限**：12 条用例适合快速回归，不足以支撑统计显著性结论；扩大评估集与引入重排（rerank）已列入下一阶段。
4. **资料覆盖影响结果**：部分失败用例的根因是资料库未覆盖该主题（如「倒伏」），属于内容缺口而非检索算法问题，
   报告与材料中应区分这两类原因。

## 六、相关接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/kb/status` | 资料库规模、向量索引状态、图谱规模、当前检索模式 |
| `POST /api/kb/reindex` | 建立/重建向量索引（可携带 `apiKey`） |
| `POST /api/kb/eval?depth=5` | 同深度对照评估（literal / semantic 分开统计） |
