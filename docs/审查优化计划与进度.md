## 1. 工作约定：每轮都能独立暂停

- 一轮只处理一个主要问题或一组紧密相关的问题；发现新问题先登记，不顺手扩展任务。
- 每轮开始先检查 Git 状态和当前代码，保留用户与其他 agent 的改动；旧验收报告作为线索，不替代本次验证。
- 每轮步骤固定为：复现/取证 → 最小修复 → 针对性测试 → 必要回归 → 更新本文 → 简短交付。
- 单轮预计超过约 3—5 个核心实现文件时，优先拆成小轮次；这不是硬限制，以能安全收尾为准。
- 不开启长期目标或定时任务，不自动部署、不推送 Git、不清理用户数据。提交/上传由用户另行要求。
- 自动测试使用 mock 和临时数据库；真实模型或 embedding 评测另列批次，先说明调用范围与凭据需求，不把付费评测混进普通回归。
- 不以“所有测试通过”代替专业性、事实准确性、浏览器可用性或公网安全验收。
- 每轮结束必须留下下一步的具体入口。额度或上下文不足时，先写清已完成、未完成、当前修改及恢复命令，不把半成品标成完成。
- 阶段安全检查通过前，不扩大部署可见范围，不开防火墙或隧道，不改账号体系。

这套安排用于降低长任务中断后的恢复成本，不承诺固定额度内能完成全部路线图。

### A01｜回答规则相互冲突，可能诱导无依据判断

状态：R01 已修复并通过离线回归；真实模型效果未复测。以下为提交 `6e1f4af` 的修复前证据，链接行号为当时位置，当前代码行号已有变化。修改和验证结果见第 7 节 R01。

修复前证据：

- [ChatController.java](D:/aic/server/src/main/java/com/nongxin/controller/ChatController.java:445) 要求第一句必须给判断，且“不许用信息不足代替判断”。

R01 方法：

1. 先收集现有单测与提示词的对应关系，不直接删除所有兜底逻辑。
2. 把一般知识问答、事实不足的排查、证据足够的条件性建议分开：事实不足时允许明确未知，并给观察/核验步骤。
3. 统一追问与方案条件，不按固定轮数强迫诊断或处方；避免原样重复问，但不能把“暂不确定”当成已经获得事实。
4. 重新限定补写正文的触发条件，避免一次正常响应又额外请求模型以凑“判断句”。
5. 增加无作物、无症状、矛盾日期、无天气、暂不确定、两轮仍缺关键数据等用例；保留确认卡和任务接入。

验收：规则中不再有互相排斥的要求；不足信息不强制诊断/用药；针对性测试与全套回归通过。真实模型效果另标“未复测”，不靠 mock 宣称幻觉已消除。

### A02｜演示额度首次计数存在异常放行风险

状态：无计数记录异常已在 R02 修复；并发扣额与一般数据库故障放行已在 R03-a 修复；R03-b 已修复直连模式下的流式来源传递并默认忽略转发头；R03-c 已把确定性本地准备前置到扣额之前，并区分耗尽与不可用状态。可信代理接入尚未启用，不等于成本护栏整体已验收。以下为 `6e1f4af` 修复前证据，当前行号已有变化。

修复前证据：[ApiKeyServiceImpl.java](D:/aic/server/src/main/java/com/nongxin/service/impl/ApiKeyServiceImpl.java) 使用 `queryForObject` 查询当天计数，再判断 null；外层异常分支会放行并返回服务端密钥。

R02 复现结果：新日期/新客户端没有计数行时，查询实际抛出 `EmptyResultDataAccessException`（预期 1 行、实际 0 行），后续递增未执行；从空记录开始的连续请求无法达到限额，状态查询也返回用量错误。修复前新增 12 项测试中有 7 项失败，旧 `CostGuardTest` 的缓存测试未覆盖此问题。

R02 修复：仅在 `currentCount` 中捕获“无记录”异常并返回 0，沿用现有递增逻辑；其他数据库异常不在此处伪装成零用量。临时 SQLite 验证首次调用创建全局/IP 两种计数、后续请求递增、顺序请求达到限额后拒绝，且新日期不修改旧日期记录。真实供应商未调用。

R03-a 结果：8 个独立服务/连接同时进入旧逻辑时，IP 限额 2、全局限额 3 的两种测试都放行了 8 次，各重复 3 次均复现。改为独立事务内按固定顺序执行带上限条件的全局/IP upsert，不先读取余量；任一限额或写入故障回滚，提交成功后才返回 Key。连接失败、缺表、锁等待超时、第二笔写入失败、写入后异常和提交阶段约束失败均已覆盖；状态错误脱敏，不混入读取失败前的部分用量。详见第 7 节。

R03-b 结果：同步/流式入口在请求线程捕获不可变的 `QuotaClient`，显式传入工作线程和额度服务；不传 servlet 请求对象、不继承线程身份。默认只采信 `getRemoteAddr()`，忽略 `X-Forwarded-For`、`X-Real-IP`、`Forwarded` 和消息体中的 `clientIp`，并显式配置 `server.forward-headers-strategy: none`。来源缺失或无效时不创建 `unknown` 配额，不提供受限演示 Key；自带 Key、未配置演示 Key、明确关闭限额保持原语义。

代理边界：这是按服务端连接来源计数，不是登录身份或每台设备身份。[Vite 配置](D:/aic/frontend/vite.config.ts) 当前把 `/api` 代理到本机后端，因此通过同一代理连接来源的用户会共享该来源限额；NAT 也可能共享出口 IP。本轮没有擅自信任回环、私网或全部代理，也未修改 Vite。后续需要识别代理后的终端用户时，必须在已知部署拓扑下单独配置可信代理、头部清洗和不可绕过的后端入口，并实测；不能直接把转发头重写策略改成 native/framework 就宣称安全。该条件纳入 R05/实际部署前核验。

R03-c 结果：增加不含凭据、不访问额度库的实际供应商/模型选择步骤，先完成消息、地址、图片和本地上下文准备，再原子预留一次额度并进入模型流程；校验实际使用的服务端模型，不能用客户端模型名代替。额度耗尽返回 429；额度核验故障、来源不可用返回 503，并附机器可读 code。SSE 已建立的 HTTP 连接仍为 200，错误事件内携带逻辑 status/code，前端可读错误提示兼容性已通过测试。上游失败不随意退额，补充回答仍共享本次预留；请求次数限额不是供应商 token/费用精确结算，不应据此宣称费用绝对受控。

原流式问题已复现并移除：旧 `clientIp()` 在独立工作线程读不到请求，导致不同来源合并到 `unknown`，而同步请求又可用伪造头改变计数键。R03-b 测试确认同源同步/流式共享配额、不同直连来源独立计数，排队后原请求改变也不会改变已捕获的来源；旧 `unknown` 历史计数未删除或迁移。

### A03｜数据归属不等于身份认证

证据：[CurrentUser.java](D:/aic/server/src/main/java/com/nongxin/service/CurrentUser.java:21) 默认返回同一个本机用户。现有服务层测试使用 resolver 模拟多个用户，不是 HTTP 登录与越权测试。

R04-a1 历史验证：使用真实上传服务、临时图片/SQLite 和 MockMvc，按模拟归属验证图片操作，未添加登录体系。当时确认 `CurrentUser.setResolver(() -> null)` 仍回落到 `local-owner`；在该模式下，即使 HTTP 请求没有身份信息和连接来源，也能读取本机所有者的测试照片。这是修复前的现状记录，不是安全验收。

R04-a2a 当前结果：已配置解析器返回 null/空白或抛 RuntimeException 时，抛出固定、无原始原因的 `IdentityUnavailable`；不采用本机身份或上次成功身份。`setResolver(null)` 被拒绝且原解析器保留；默认实例和显式 `reset()` 仍采用本机共享模式。数据控制器统一返回 `503 / IDENTITY_UNAVAILABLE` 和 no-store，不把解析服务故障假称为已实现的登录/重认证流程。旧空身份现状测试已改成“默认共享模式仍可用”与“解析失败拒绝”的分离测试。生产代码当前没有设置登录解析器，故这一修复不能作为公网多用户安全声明。

R04-a2b1 当前结果：同步/流式聊天入口解析并捕获一次不可变数据归属，流式队列只保存该快照和既有 QuotaClient，不复制请求对象/请求线程状态。CurrentUser 在受控回调内使用快照，finally 恢复原上下文或 remove；不隐式继承到子线程。聊天的读图、工具查询和补充轮复用入口归属；AgentContext 使用同一身份而不再统一写 web-user，身份不因此加入模型提示词。入口解析失败在读图、取 Key、扣额和模型之前返回 JSON 503；已开流内的工具/补充轮身份异常终止当前流程，返回携带逻辑 503/code 的 SSE error，不吞掉异常后假称完成。

R04-a2b2 当前修复：田块、会话、任务、上传四类控制器共 24 个 HTTP 映射方法，均在控制器入口捕获并使用同一 CurrentUser 快照；参数业务校验、跨服务查询/写入及响应对象构造均在作用域内。上传的受检 IOException 可原样传播，正常和异常退出均恢复上下文。没有添加全局过滤器，天气、健康检查及启动钩子没有被套入交互请求快照。

剩余边界：快照是控制器入口时点的归属，不是登录认证、实时撤权或令牌有效期校验；默认部署仍为本机共享模式，不直接采信客户端 userId/身份头。Spring 的参数绑定、JSON/multipart 解析发生在控制器之前，本轮不把这些步骤纳入身份作用域；新增入口、直接服务调用及新增异步工作仍需显式接入。UploadService 的系统清理继续独立于 CurrentUser；TaskService.mergeDuplicates 的旧实现内部仍调用按 CurrentUser 查询/删除的方法，本轮未改变其维护策略，不能概括为所有启动维护都与身份无关。文件/数据库故障、并发关联变更等事务一致性另留 R04-b2。

R04/R05 方法：

- 核对会话、田块、照片、任务、执行记录、资料操作每个入口，不只看 list 查询。
- 查照片删除/过期清理/关联删除是否保留仍被使用的文件；旧版本数据库在副本上迁移，验证备份可恢复。
- 检查网络二维码、开发服务器监听、手机模式脚本和接口是否可能扩大数据可见范围；本轮不实际开启手机模式。
- 后续接登录时使用请求级身份并对匿名失败关闭访问，不能把无法识别的用户回落到本机所有者。
- 自定义供应商地址不能仅以 `https://` 开头就视为公开可信；查内网地址、重定向、凭据转发及输入上限。

验收：先写清本机单用户边界，验证现有功能不会误跨归属或误清理。真正登录/公网部署属于单独实施任务。

### A07｜启动清理未考虑田块与任务归档

状态：R04-b1 已修复清理保留条件；R04-b2b2b1 已修复文件失败后的假成功；R04-b2b2b2a 已接入逐张事务和恢复副本；R04-b2b2b2b1 已增加事务内状态复核；R04-b2b2b2b2 验证了竞争写入先占用/提交的 SQLite 窗口。R04-b2b2b2b3 又复现并修复清理先提交后会话仍保存失效图片引用的问题；R04-b2b2b2b4 已修复图片先被删除时归档更新的空指针/零行结果问题。以上均为离线结果，未清理真实数据库和文件；跨进程及崩溃恢复仍未完成验收。

修复前证据：[UploadController.java](D:/aic/server/src/main/java/com/nongxin/controller/UploadController.java) 的 ApplicationRunner 启动时调用 `cleanupUnreferenced()`；[UploadService.java](D:/aic/server/src/main/java/com/nongxin/service/UploadService.java) 只按 `referenced_at IS NULL AND created_at < cutoff` 选择清理对象，没有检查 field_id、task_id 或其他业务引用。田块/任务照片不一定保存过聊天引用，因此不能把“未用于聊天”直接等同于“可丢弃”。另确认 ConversationController 先保存对话、再单独 markReferenced，引用时间标记不能作为唯一依据。未查看用户实际记录，不声称已经发生真实误删。

R04-b1 结果：修复前 22 项用例中 19 项失败，临时归档照片和缺失标记的已保存对话图片确实被删。现在仅把 field_id、task_id、referenced_at 全为 null 且上传时间可确认为过期的照片列为候选；非 null 的空白/悬空旧关联也保守保留，不擅自修正记录。有候选时再逐条读取所有归属的已保存对话，识别图片 ID、请求快照和文本/内联链接中的 ID；实际引用会阻止清理，不要求标记时间已补齐，也不自动改写标记。

不确定策略：候选或引用查询失败、对话 JSON 损坏/重复键/多余根值、图片引用结构无法识别，均在第一次删除前跳过整批清理，日志只记类型和固定提示；上传时间格式不明的个别照片保留；保留天数小于 1 时跳过。系统级清理不读取 CurrentUser，也不会按 local-owner 隐藏其他归属的引用。没有候选时不扫描对话。

R04-b2b2b1 结果：自动清理遇到 IOException（含 AccessDeniedException）或 SecurityException 时，跳过该张元数据 DELETE、保留登记、不累加成功数量；其他已核实候选可继续处理。日志只记录固定说明、ID 和异常类型，不输出原始错误消息或文件路径。临时非空目录导致真实删除失败时，也不递归删除其内容。文件本来缺失且满足原有候选/引用规则时，仍允许注销残留登记；旧恢复目录和无登记文件不扫描、不清扫。

R04-b2b2b1 的历史边界：只保证文件错误后保留登记、不报成功，不能恢复 unlink 已发生的字节。R04-b2b2b2a 已在此基础上复用手动删除的私有恢复副本、逐张独立事务与 JVM 内同图锁；明确回滚且未开始提交时尝试无覆盖恢复，提交/回滚不明或恢复冲突时保留副本供核对。只有 DELETE 恰好一行、事务确认提交且本次副本清理完成才加 1。系统清理仍不解析 CurrentUser，失败照片不计数、其他已核实候选可继续。文件本来缺失时无副本，允许注销满足条件的残留登记；旧副本不扫描清扫。

R04-b2b2b2b1 结果：候选的独有备份完成后、unlink 之前，在本次删除事务中重新读登记及所有归属的已保存对话。登记不存在或 Stored 中已读字段发生变化（包括关联、上传时间、扩展名、备注等），即取消该候选；新增对话中的图片 ID、快照或内联引用也阻止删除。单图复核查询失败或新出现的坏 JSON 会先回滚/清理本次未使用的副本，再停止剩余候选，不能恢复此前已完成的其他清理，也不会抹掉已确认计数。最初整批引用核验仍保留，初始状态不明时任何候选都不会被删除。

R04-b2b2b2b2 新证据：源码使用 sqlite-jdbc 3.45.3.0，未显式设置 journal_mode、busy_timeout、连接初始 SQL 或事务模式。新建测试库实测为 DELETE 日志、busy_timeout 3000ms、read_uncommitted=0，JDBC 初始 autocommit=true、SERIALIZABLE 隔离、DEFERRED 事务模式；没有读取真实业务库，不能据此断言旧库/运行环境也是这些值。两个独立线程/连接在复核后执行真实归档、markReferenced 或会话服务保存：DELETE 模式下由测试外层事务保持写入未提交，WAL 补充模式下直接调用服务自动提交；清理随后真实 unlink、尝试 DELETE，均得到真实 SQLite BUSY 类错误，原有回滚恢复保住原图和登记，成功计数为 0。竞争写入最终可见、无恢复副本残留，后续清理也会保留已归档/引用照片。没有模拟 SQL 失败来替代并发行为。

R04-b2b2b2b3 结果：旧 ConversationController 的“校验图片 → 保存对话 → 标记引用”是分开的。临时库复现了清理已提交但新/旧对话仍被写入失效图片，以及标记引用失败后对话已变更。现在保留原先输入/权限清洗，再于单次保存事务内先按 ID + 当前归属确认每张有效图片并用 COALESCE 登记引用，要求各张更新恰好一行，然后才保存对话；缺图、部分写入或数据库故障回滚，不提前返回成功。已有引用时间不覆盖；初始校验就不存在/不属于本人的附件仍按旧行为过滤，文本和历史缺图保存兼容。

当前边界：会话引用一致性保护只接入 HTTP 会话保存入口。直接 ConversationService.save / markReferenced 的旧调用没有自动变成完整协议，其他调用方不得据此假设跨步骤事务；字段/关联对象并发变化另列。提交后确认丢失可能导致 503 但记录已存在，必须刷新核对，不能把所有失败都解释为“未保存”。WAL 仅设置在测试库；已有单连接 Hikari 及竞争先后顺序验证，不是所有超时/部署拓扑或跨进程测试。Stored 无不可重用版本号，外部文件缺失/替换、ID 重用、性能、崩溃/断电及历史丢图未验收。R04-b2b2b2b4 已把归档 UPDATE 与响应快照放入同一事务，核实影响行数并处理记录消失；DELETE/WAL 的清理/手动删除先提交窗口均返回明确冲突，不再 null 进入 card。两个编辑请求相互覆盖旧字段和归档后主动删图不属于本轮保护，不声称真实数据发生过该问题。

### A08｜上传保存失败遗留文件与不确定提交

状态：R04-b2a 已修复并通过离线回归，详见第 7 节。不是崩溃恢复或全生命周期一致性验收。

修复前证据：UploadService.store 用可覆盖的固定 `.tmp` 文件名暂存，以 REPLACE_EXISTING 移动为最终图片，然后在无显式事务的情况下 INSERT 元数据并再次读取。数据库写入失败会留下图片；文件写入/移动失败未清理暂存文件；同 ID 的既有文件可能被覆盖。仅在隔离测试中复现，没有扫描或推断真实用户目录存在这些问题。

R04-b2a 修复：保留前置归属/关联/图像校验；原子分配唯一暂存文件，写完后启动数据库事务，先全归属核对 ID 未占用，再以不覆盖方式移动文件、INSERT 一条元数据、提交。只在提交正常返回后报告成功，直接返回本次元数据，避免成功提交后第二次查询失败或返回 null。明确拒绝加入未完成的外层事务，避免提前报成功或在单连接池中等待另一连接；当前生产上传调用方是无外层事务的 UploadController。

补偿边界：只有本次移动已确认成功、事务已明确回滚且尚未开始提交，才删除本次新建的最终文件。提交调用开始后发生异常，即使后续 rollback 返回成功，也不能排除先前提交已经生效，因此保留图片；回滚结果不明也保留。部分写入失败的独有暂存文件会尝试清理；补偿删除失败仅记录，保留产物，不覆盖主错误。旧 `.tmp`、旧图片和其他归属记录不被清扫或改写。移动抛错可能已产生目标文件，不贸然删除无法确认归属的目标。

错误响应：本次保存持久化异常映射为固定 `503 / UPLOAD_SAVE_UNAVAILABLE` JSON 和 no-store，不向客户端返回原始 SQL、路径或原因；提示先刷新影像列表核对再重试。原有输入/归属校验语义不变。新增应用日志使用 ID、阶段及异常类型，不输出原始异常；Spring/JDBC 的底层诊断日志不在本轮全局脱敏范围内。

剩余边界：这不是文件系统与数据库的原子事务，也不承诺进程崩溃、断电或外部并发篡改目录时自动恢复。提交/移动结果不明或清理失败可保留额外图片/暂存文件，其中没有元数据的产物不会出现在界面，也不能由当前自动清理发现；需后续运维核对，不做全目录自动删除。没有为重试增加幂等请求 ID，不能在结果不明时盲目重传。手动删除、自动清理、并发关联变化与旧数据修复仍未完成。

### A09｜手动删除文件失败仍注销图片并报成功
