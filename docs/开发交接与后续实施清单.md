## 一、项目目标与不可违背的要求

作品名称暂定“农心 Agent”，主要对齐 AIC“AI+农业”赛题五：农业智能体与大模型决策服务。竞争力应落在专业性、可操作性、自然交互、检索准确性，而不是页面模块数量。

建议围绕这条产品主线推进：

**说清农情 → 补充必要信息 → 查到可核验依据 → 给出有条件的建议 → 用户确认加入任务 → 记录执行和复查结果。**

必须保留的要求：

1. 前后端分离：React + TypeScript + Vite 前端，Java 21 + Spring Boot 后端。不要改回全栈 JavaScript，也不要为了托管平台兼容性替换 Java。
2. 事实优先：没有录入的田块、作物、天气、执行记录和评测指标就不能假装存在。未知必须显示未知；模型判断、规则估算、用户陈述、实测数据分开表达。
3. 视觉延续当前深绿侧栏、清爽工作区和农业品牌素材。克制、实用、阅读舒适，避免霓虹渐变、机器人头像、假数据大屏和无意义的仪表盘。
4. 定位、天气、时钟仍放在侧栏紧凑模块，不重新占据主聊天页面。设备或城市位置不能等同于田块位置。
5. 模型供应商、模型名称和 API 地址可配置；密钥不能进源码、Git、数据库、日志、导出文件或截图。
6. 确认卡必须逐题保留答案，通过“提交并继续”整理成一条包含问题和答案的用户消息，不能再次变成单击选项覆盖聊天框。
7. 建议不是事实，加入任务不代表已经执行；没有原文核验不能宣称官方依据，没有专家验证不能宣称专家诊断。
8. 用户早期提供过密钥，但交接不复制密钥。真实测试需要正确供应商地址、当前有效凭据和适当授权，不猜接口、不批量消耗额度。

### P0-2 完成真正的流式对话，而非打字机动画

代码入口：

- 前端：`frontend/src/lib/chat.ts`、`frontend/src/App.tsx`。
- 后端：`ChatController.java`、`ChatStreams.java`、`AgentRunner.java`、`CompletionStream.java`、`StreamObserver.java`。

方法：

- 保留现有 `/api/chat`，避免破坏模型设置中的连接测试；聊天主流程使用 `/api/chat/stream`。
- 校验上游 SSE 的 UTF-8 分片、CRLF、心跳、结束原因以及工具调用的 index/name/arguments 分片；不向用户展示 reasoning 字段、密钥或原始工具参数。
- 前端最终答案以 `done` 为准；没有正常结束信号的断开不得标记为成功。
- 工具阶段展示“正在核对资料”等真实状态；不要在下一工具轮把上轮文本重复拼进最终答案。确认卡和方案卡应在结构完整后展示。
- 检查多轮工具调用时 `reset` 的显示行为，避免闪烁、丢失可见片段或让半成品看起来像最终建议。
- 网关忽略 `stream=true` 返回正常 JSON 时，可以接收同一请求结果并明确说明；不要静默再发一次付费请求，也不要把整段结果伪装成实时流。
- 增加消息/事件总大小上限，而不只是单个缓冲区上限；检查前后端对错误、空 JSON、数组等异常形状的验证。
- 后端补充 MockRestServiceServer 和 MockMvc 测试：文本增量、工具分片、多轮卡片、JSON 兼容返回、401/429/5xx、截断、长度限制、无有效结果。

特别审查：`AgentRunner` 当前仍有“工具已有产出后供应商失败，返回 degraded 结果”的兼容逻辑。应明确把“部分完成/可重试”传给前端，不能因为已有工具结果就把失败悄悄显示成正常完成。

验收：离线可控流中，第一段在最终完成前可见；最终正文没有重复；异常不伪装成功；卡片仍可正常统一提交。

### P0-3 停止、失败、保存与重试形成一致状态

方法：

- 建议把聊天状态明确为待发送、保存中、生成中、完成、中断、保存失败，避免多个互相矛盾的布尔值。
- 用户问题先保存再发模型；保存失败时不调用模型，保留内容并允许单独重试保存。
- 回答完成但保存失败：保留屏幕内容，显示请勿刷新，重试保存不应重新消费模型。
- 手动停止/超时/断网：保留已收到的文字并标注“回答未完成”，排除在后续完整答案历史之外。
- 重试复用同一个用户问题及其快照；双击按钮、快速停止后重试不能新增重复问题。
- 重试使用当前有效模型设置，不保存历史密钥；若用户更换供应商/模型，明确其影响，不声称会复现相同答案。
- 对同一会话的保存串行化或加版本冲突检查，防止迟到的旧请求覆盖新消息。确认手动“重试保存”也有提交锁。
- 前端 AbortController 与后端取消相互配合；检查超时、断连、线程池拒绝后的资源释放。网络阻塞的上游连接是否立即终止需要验证，不保证停止就停止计费。
- 检查关闭页面、刷新后恢复、切换工作页面再返回、后端临时离线的表现。

验收：同一问题连续失败两次再成功，数据库仍只有一条对应用户消息；中断状态刷新后可识别；密钥和上游内部报错不出现在持久化内容中。

### P0-4 上下文隔离和历史管理

方法：

- 同一会话有消息后切换关联田块必须新建会话，保留旧聊天，不把其他田块历史带过去。
- 请求建立时固化 field/weather 快照，字段为空就为空。重试不自动使用后来修改的田块和新查询的天气。
- 天气默认不附带，用户勾选后发送；更换城市、清除位置、切换会话时核对勾选状态。天气日期、来源、城市近似位置应可查看。
- 历史天气不能被当成现在天气；过期快照应显示时间并提醒重新查询，而不是悄悄更新原问题。
- 结构化追问需要进入模型历史，否则模型看不到此前问了什么。保留明确“暂不确定”，不把它转成猜测。
- 当前只发送最近 20 条有效消息，要让用户知道这是上下文窗口限制。事实记忆/长对话摘要不是当前已实现能力；以后做摘要只压缩已知事实并保留来源、时间、未知项，不编造记忆。
- 重命名只 PATCH 标题，不能重写消息；删除必须二次确认、说明不可恢复，失败时保留列表。删除会话不删除田块或已创建的农事任务。
- 当前历史列表已改为全量显示；规模变大后再按实际需求做分页/虚拟列表，不提前大改。

验收：甲田和乙田的独有内容不会混入对方请求；历史重命名刷新后保留；取消删除不产生请求；删除失败不丢记录；中文长标题和移动宽度下操作按钮可用。

## 五、P1：让农业建议有可核验的出处

目标：从“模型说得像”升级为“能查看原文，知道何时何地适用”。

方法：

1. 先选择团队熟悉且有资料条件的 1—2 类作物和一个真实地区作为示范范围，由用户确认，不默认替用户确定研究对象。
2. 建立来源登记：原文标题、机构、URL、发布日期、抓取日期、地区、作物、生育阶段、版本、授权/许可、审核状态。
3. 数据结构建议分为 `knowledge_documents` 与 `knowledge_chunks`，片段保留文档 ID、章节/页码及定位信息；不要只有一个相似度分数和一段无出处文字。
4. 当前 17 条草稿保留为未核验材料，不批量改成“官方已审核”；逐条对照原文才能改变状态。
5. 先做可控的关键词检索与元数据过滤，再根据真实评测决定是否增加向量检索和重排。不要为了展示技术栈先堆一个未评估的向量库。
6. 模型仅能引用实际检索命中的来源 ID；后端校验引用 ID 是否存在、是否属于本次检索结果。来源不可用时明确标注。
7. 答案区区分“你提供的事实”“资料支持的判断”“仍需核实的信息”。来源卡展示原文链接、日期和适用条件。
8. 不足以确认病害、农药登记和用量时，输出核查步骤，不补写剂量。涉及当前规定和登记信息时应访问权威原文核验，不能依赖过期资料或模型记忆。

验收：每条展示的引用能对应真实原文；没有命中时明确说没有依据；不相关地区/作物的材料不会被无条件用于处方；有一组人工核验的检索用例，准确率依据真实结果计算。

创新点：不是给所有回答贴上“可信”标签，而是把依据、适用条件和缺失信息一起展示，让用户知道哪一步还需要现场确认。

## 六、P2：把建议做成能执行、能复查的农事闭环

已有任务和观察记录，不要另起一套互不关联的“农场管理平台”。

方法：

- 方案项规范为：做什么、适用条件、建议时间/时间窗口、具体方法、风险与禁忌、所需物料、依据、复查时间或触发条件。缺失字段写待确认，不能补造。
- AI 方案先是草稿；用户确认后创建任务。重复确认必须用 sourceMessageId/方案项 ID 幂等处理。
- 任务状态逐步扩展为待确认、待执行、已执行待复查、已完成/取消；完成任务需用户提交实际记录，不由 AI 自动宣告。
- 执行记录与任务、田块、来源消息关联；返回聊天讨论时明确携带用户记录，而非把之前建议当成已经执行。
- 复查结果可包含文字和之后支持的照片；模型基于新证据调整建议，并说明哪里变化、为什么变化。
- 新增数据库结构需要版本化迁移和备份，不能靠清库解决字段变化。
- 到期提醒先做页面内可见提醒；真正定时推送需要独立调度、用户选择和送达状态，不做虚假的自动提醒。

验收：一条方案能追到依据，一项任务能追到来源建议，一条执行记录能追到田块；完整走通一次“建议—确认—执行—复查”，缺数据不自动补齐。

## 七、P3：图片辅助排查与移动端体验

> **已完成（2026-09-11）**：走视觉大模型路线，**不做自训练检测模型**（决策依据见 `docs/P3-验收报告-2026-09-11.md` 第一节）。
> 已交付：模型视觉能力判定与"不支持时明确拒绝"、图片上传/压缩/EXIF 清理/预览/删除与生命周期管理、
> 拍摄引导、三段式输出规范（图上现象 / 可能原因 / 还需信息，不确诊、不伪造置信度）、移动端作曲区。
> 下面的原始要求保留作对照。

图片能力不是直接把上传按钮改成 image 就算完成。

方法：

- 先确认所选供应商/模型确实支持视觉输入和所需工具调用；模型不支持时明确提示，不发送伪视觉请求。
- 图片上传需类型与大小校验、预览、删除、压缩、EXIF 隐私清理；后端存储做授权和生命周期管理，不把大图或 base64 混进聊天文本字段。
- 引导用户按全株、病部近景、健康对照、环境信息提供照片；界面说明补拍原因，避免一次给十几个表单字段。
- 输出分为“图上能看到的现象”“可能原因与排除方法”“还需哪些信息”。不根据单张照片宣称确诊，不伪造识别框或置信度。
- 如果做专用识别模型，单独报告真实数据集来源、划分方式、模型大小、推理耗时和评测结果；不要将通用视觉模型输出包装成自研检测算法成绩。
- 手机端优先保证输入框、键盘弹出、照片预览、逐题确认和提交按钮可用；天气继续保持紧凑，不压缩主要工作区。

验收：支持和不支持视觉的模型均有明确流程；上传失败不丢草稿；用户可删除附件；结果可解释且保留不确定性。

## 八、P4：先做好数据隔离，再做扫码与微信

分清两个不同目标：手机扫码打开网页，不等于微信身份登录或跨端会话绑定。

方法：

1. 第一阶段可先做响应式网页和“扫码在手机打开”。二维码仅携带可访问的 HTTPS 页面地址，不能放 API Key、聊天内容或凭据；手机访问不能用电脑的 localhost 地址。
2. 公网前补账号/会话鉴权、资源归属与 API 权限校验。所有田块、任务、会话、图片查询都按用户隔离，不能只在前端过滤。
3. 加入 HTTPS、限流、请求体限制、日志脱敏、备份、删除策略与基本安全测试。自定义供应商地址需防 SSRF：协议、目标主机、IP 范围、重定向和 DNS 等都要核查。
4. 真正微信登录/绑定需用户具备相应平台资质与配置；接手时查阅微信官方最新文档，明确公众号/开放平台/小程序的差异，不承诺所有账号都能免配置扫码登录。
5. 跨端绑定使用短时效、一次性、有状态的票据；电脑端确认、过期作废、防重放。不要用长期访问令牌直接生成二维码。
6. 手机端重新确认允许发送的位置/天气，不能自动沿用另一设备定位。供应商凭据是否跨端共享应由用户选择并采用安全方案。

验收：甲用户访问乙用户资源返回拒绝；过期/重复票据无法绑定；二维码无敏感信息；手机和电脑的同一用户会话可续接，退出后权限失效。

## 九、P5：真实评测与竞赛交付

方法：

- 对照用户提供的赛题与附件原文整理要求，不猜评分权重。时间安排和后续通知以赛事最新原文核验为准。
- 建立版本化测试集，覆盖信息充分、信息不足、错别字、无田块、天气缺失、互相矛盾的农情、资料无命中、模型失败、连续追问等情况。
- 记录真实指标：引用匹配、无依据断言、必要信息追问、任务可操作性、请求首段延迟/总耗时、失败恢复、用户完成步骤。展示样本量与评测方法，不只放一个百分比。
- 通用模型直接问答作为基线；与加入资料检索、上下文约束、确认卡、闭环功能后的结果比较。没有实际实验就写“待评测”。
- 请农学老师或真实使用者按明确标准评分，区分专家反馈、用户体验意见和系统自动测试。
- 技术方案、PPT、演示视频都区分已实现、局限和后续规划。视频采用真实操作，演示数据明确标注且与用户真实工作区隔离。
- 整理原创代码、开源依赖、图片生成记录、资料授权与引用，避免把第三方项目或模型说成全部自主研发。

推荐演示主线：从一个具体但信息不全的问题出发，展示确认卡统一提交、来源核验、带条件的建议、确认任务和复查；再展示一次失败恢复，体现可靠性。

## 十二、每个阶段的交付格式

每次交付都回答这五件事：

1. 本轮实现了什么，用户如何操作。
2. 改了哪些关键文件和数据结构，如何兼容旧记录。
3. 哪些测试实际通过，哪些没做；真实模型测试和 mock 测试分开写。
4. 是否存在数据迁移、凭据、部署或使用限制。
5. 下一步最小可执行任务是什么。

本次整理仅新增交接文档，没有继续修改聊天功能、修复测试、重启服务或上传仓库。
