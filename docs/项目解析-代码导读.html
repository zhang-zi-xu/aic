为什么先保存再问模型

App.tsx:220 先 persist(pending) 落库，成功才发请求。这是为了保证"屏幕上出现过的用户消息，数据库里一定有"——如果保存失败，用户会看到「回答尚未保存到数据库，请勿刷新页面」和一个独立的「重试保存」按钮，模型根本不会被调用。反过来，如果回答失败但保存成功，屏幕上保留的是一条标着 status:'interrupted' 的消息，它会永久留在历史里但不会进入后续对话上下文（lib/chat.ts:24）。

三个值得注意的设计

  • 会话消息整段存 JSON（conversations.messages_json）。不是拆成消息行。代价是不能按消息查询，收益是读写一次成型、天然保序。单会话上限 2MB（ConversationService.java:41）。
  • 答案缓存的键不含问题原文。原文会被哈希成 SHA-256 前 32 位十六进制（AnswerCacheServiceImpl.java:110），避免把用户问题直接当主键落库。而且含天气快照的请求根本不缓存——天气随时效变化，缓存会让过期的施药窗口被当成新答案。
  • 唯一索引带 WHERE 条件：idx_tasks_plan_item(source_message_id, plan_item_id) WHERE 两者均非空。SQLite 视 NULL 为互不相同，所以迁移来的历史任务（这两个字段为空）不会互相冲突。

版本化迁移

service/SchemaMigrationService.java，201 行，是 P2 阶段最重要的基础设施之一。它的契约很明确：

  1. 启动时读 schema_version 表的最大 version；表不存在则用"有没有 farm_tasks 表"判断是全新库（0）还是基线库（1）。
  2. 版本已达标 → 直接返回，不产生备份（避免每次启动都堆积文件）。
  3. 需要升级且是老库 → 先备份。备份用 VACUUM INTO 做一致性快照，失败才退回文件复制（:104）。
  4. 执行迁移步骤，每一步都可重复执行：addColumn() 先查 pragma_table_info，列存在就跳过。所以中断后重启不会卡住也不会重复加列。
  5. 记录新版本号。

两个静态方法定义了铁律：

TaskStatus.java:52–65状态机的全部规则
/** 不依赖记录即可直接切换到的目标状态。 */
public boolean allows(TaskStatus target) {
    if (target == this) return true;
    return switch (this) {
        case PENDING_CONFIRMATION -> target == PENDING || target == CANCELLED;
        case PENDING              -> target == CANCELLED;
        case AWAITING_REVIEW      -> target == PENDING || target == CANCELLED;
        case COMPLETED, CANCELLED -> target == PENDING;
    };
}

/** 目标状态是否必须提交执行/复查记录才能进入。 */
public static boolean requiresRecord(TaskStatus target) {
    return target == AWAITING_REVIEW || target == COMPLETED;
}

allows() 里根本没有 AWAITING_REVIEW 和 COMPLETED 这两个目标状态——所以任何"直接改状态到已完成"的请求都会在 allows() 之前被 requiresRecord() 拦下并抛 IllegalStateException → HTTP 409。这就是 P2 报告里第 3 步验到的「无执行记录直接标已执行待复查 → 409」。

① 系统提示词就在 Java 里。ChatController.java:320–378 的 buildSystemPrompt() 是一个约 3000 字的中文长字符串。整个产品的"人格与纪律"都在这段文字里：语气、回答结构、说话方式、事实纪律、工具使用规则、专业红线。它不是一个配置文件——改提示词就是改 Java 源码再重新打包。这是当前架构最粗糙、也最需要小心的地方之一。

lib/chat.ts — 流式解析

80 行，是全前端最需要小心的一块。三个导出函数：

requestHistory()（:23）把前端消息转成模型历史。两个动作：先 filter() 掉 status:'interrupted' 和 degraded:true 的消息（未完成的回答不能当作完整答案喂回去），再 slice(-20) 只留最近 20 条。然后把附件数据、此前的确认卡、方案、风险结果按特定格式拼进 content——每条都带一句声明，例如 【此前生成的建议，未经用户确认执行】。

retryMessages()（:14）决定"重试"重发什么。三种情况：最后一条是 user（说明请求根本没发出去）→ 原样重发；最后一条是失败/半完成的 assistant 且前一条是 user → 切掉最后一条 assistant，重发那条 user；其余 → null（不可重试）。这就是"重试不产生重复问题"的实现。

streamChat()（:35）是 SSE 解析器。它要处理的问题比看上去多：

  • UTF-8 字节切分：中文字符可能被 TCP 分片从中间切开。TextDecoder 用 {stream: !done} 保证跨块的半个字符不被解码成乱码。
  • CRLF 与多行 data：replace(/\r$/, '') 去掉行尾回车；多个 data: 行用 \n 拼接后再 JSON.parse（SSE 规范要求）。
  • done 之前的一切都不算成功：循环条件是 while (!result)，只有收到 done 事件并校验了内容才 return。done 里还要再验一次：reply 非空、或至少有 plan/risk/clarify 之一，否则抛"模型没有返回有效内容"。
  • 提前 EOF：if (done && !result) throw new Error('回答连接中断，已收到的内容不是完整答案，可重试这条问题。')
  • 2MB 上限与 finally 里的 reader.cancel() 释放。

07红线与不变量

改代码前先过一遍这十条。踩中任何一条，改动大概率会被推翻或引入回归。

  1. 依据只能来自本次（或本会话此前）真实检索命中的 chunkId。防线共五层，任何一层都不能绕过。新增任何"生成依据"的路径都必须接进白名单校验。
  2. 任务状态推进必须由用户提交的事实驱动。completed 与 awaiting_review 不能通过 changeStatus 到达。AI 不能宣告任务完成。
  3. 测试绝不能连真实数据库。所有 @SpringBootTest 必须用 @DynamicPropertySource 指向临时 SQLite 文件。历史上 CostGuardTest 曾写进用户真实库的 answer_cache 表。
  4. 数据库结构变更走 SchemaMigrationService，不要删库。每一步必须幂等（用 columnExists / tableExists 先判断）。升级前会自动备份到 server/data/backup/。
  5. 密钥不落地。只存 sessionStorage；不写数据库、源码、日志、导出文件。ConversationController.rejectPrivateKeys() 是最后一道闸。测试密钥也不要写进任何文件。
  6. 未核验 = 未核验。本地草稿的 reviewStatus 必须保持 unverified，UI 上必须显示"本地草稿 · 未核验"。只有逐条对照原文才能改状态。
  7. 缺数据就写"待确认"，不补造。用量、物料、时间窗口缺失时保持「待确认」字样，不要在对话里补一个看起来合理的值。
  8. 未完成的回答不进上下文。status:'interrupted' 与 degraded:true 的消息必须被 requestHistory() 过滤掉。前端与后端各有一处这样的过滤。
  9. 确认卡逐题保留答案。不能退化成"点一下选项就发出去"。必须支持自填与"暂不确定"，必须合并成一条完整用户消息。
  10. 外部依赖全部可降级。向量、图谱、天气、地理编码、缓存、用量计数——任何一个挂掉都不能阻断主流程。新增外部调用时照这个模式写。

9.1 README 的检索数字无法用现有接口复现

这是最重要的一处。README 第 93 行称：

README 原文

「同一评估集下，关键词 Top3 命中率 25.0%（3/12）→ 三路混合 91.7%（11/12）；该数据为本地哈希向量模式（离线可跑）测得。」

但我对正在运行的后端调用评估接口，得到的实际结果是：

POST /api/kb/eval?depth=3 与 depth=5本机实测，2026-09-11
depth=3  literal : 25.0% (2/8) -> 25.0% (2/8)   semantic: 75.0% (3/4) -> 75.0% (3/4)
depth=5  literal : 25.0% (2/8) -> 25.0% (2/8)   semantic: 75.0% (3/4) -> 75.0% (3/4)

vectorKind: none | vectorReady: false | indexedModel: local-hash-ngram-256

三个问题叠在一起：

  • 数字对不上。现在的口径把 12 条用例拆成 8 条 literal + 4 条 semantic 分开统计，而 README 用的是合并的 3/12 与 11/12。两套分母不同。
  • "关键词 25%"这个数字现在对应的是 literal 子集（2/8），不是全部 12 条。全量关键词命中实际是 5/12 ≈ 41.7%，因为 4 条 semantic 用例里有 3 条居然被纯关键词命中了。
  • 91.7% 在当前代码下无法复现。修正后的评估代码明确不把本地哈希向量在 semantic 类上的命中计入成绩（RetrievalEvalController.java:95），所以本地哈希模式的理论上限只有 literal 那 8 条。91.7% 应该来自口径修正之前的旧评估代码。

有意思的是，docs/P1-检索用例与来源登记.md 最后一节已经解释过这两组数字口径不同，docs/RAG-评估方法与口径.md 更是专门写了一节「在配置真实语义模型之前，任何"命中率提升"的数字都只能表述为「检索管线自检结果」，不得作为"语义检索效果"写入方案或答辩材料」。也就是说：口径文档已经修正了，但 README 的这句话没有跟着改。如果这份材料要提交或答辩，README 第 93 行是当前的合规风险点。

另一处状态

同一个接口显示 embeddingConfigured: false——当前运行的后端没有配置 embedding 密钥，所以实际跑的是纯关键词（+ 图谱）。而 kb_vectors 表里躺着 44 条 local-hash-ngram-256 的向量，是之前本地哈希模式留下的。这两件事不矛盾（ready() 要求模型名一致，当前模型是 BAAI/bge-m3 所以不 ready），但如果你在材料里写"已启用向量检索"，与运行现状不符。
